### 传统加载器的限制

#### 你之前的简单加载器

假设你已经实现了这样的加载器：

```asm
; 简单的内核加载（Stage 2）
[BITS 16]
[ORG 0x8000]

KERNEL_SEGMENT equ 0x1000       ; 加载到 64KB (0x10000)
KERNEL_SECTORS equ 200          ; 100KB (200 个扇区)

load_kernel:
    mov ax, KERNEL_SEGMENT
    mov es, ax
    xor bx, bx
    
    ; 使用 BIOS INT 13h 读取扇区
    mov ah, 0x02                ; 读扇区功能
    mov al, KERNEL_SECTORS      ; 扇区数
    ; ... CHS 参数设置
    int 0x13
    
    ; 进入保护模式
    ; 复制内核到 1MB
    ; 跳转执行
```

#### 这个加载器的问题

**限制1：实模式最多访问 1MB 内存**
```
实模式寻址 = 段:偏移
最大地址 = 0xFFFF:0xFFFF = 0x10FFEF (约 1.06MB)

但实际可用：
  0x00000 - 0x9FFFF = 640KB（低端内存）
  0x100000+         = 需要保护模式！
```

**限制2：需要"二次复制"**
```
磁盘 → 64KB 缓冲区（实模式可访问）
     ↓
  进入保护模式
     ↓
64KB 缓冲区 → 1MB 最终位置
```

**问题：**
- ❌ 浪费时间（双重复制）
- ❌ 浪费内存（需要临时缓冲区）
- ❌ 内核大小受限（缓冲区大小）

**限制3：内核大小硬限制**
```
如果内核 > 200KB？
  → 需要多次加载
  → 代码复杂
  → 容易出错
```

## 第二部分：核心技术

### 实模式内存限制详解

#### CPU 寻址方式演进

**8086 时代（20 位地址总线）：**
```
段寄存器：16 位
偏移：    16 位

物理地址 = 段 × 16 + 偏移
         = 0xFFFF × 16 + 0xFFFF
         = 0x10FFEF
         ≈ 1.06 MB

但！CPU 只有 20 根地址线
  → 地址 > 1MB 的部分被"回绕"
  → 0x10FFEF → 0x0FFEF (回绕到开头)
```

**80286 时代（24 位地址总线）：**
```
保护模式：可以访问 16MB
实模式：  仍然只有 1MB（兼容性）

问题：如何访问 1MB 以上的内存？
  → 必须切换到保护模式！
```

**80386 时代（32 位地址总线）：**
```
保护模式：可以访问 4GB
实模式：  还是只有 1MB

但！发现了一个"漏洞"：
  → Unreal 模式（Big Real Mode）
  → 可以在实模式代码中访问 4GB！
```

#### 实模式的三大限制

**限制1：段寄存器只有 16 位**
```asm
mov ax, 0x1234
mov ds, ax          ; DS = 0x1234
mov si, 0x5678
mov al, [ds:si]     ; 访问 0x1234×16 + 0x5678 = 0x179B8
```

最大偏移 = 0xFFFF = 64KB
最大地址 = 0xFFFF×16 + 0xFFFF ≈ 1MB

**限制2：BIOS 中断只在实模式工作**
```
INT 13h (磁盘I/O)  ← 实模式
INT 10h (视频)     ← 实模式
INT 15h (内存检测) ← 实模式

进入保护模式后：
  → BIOS 中断不可用
  → 必须自己写驱动！
```

**限制3：不能直接写入高端内存**
```
想要写入 1MB (0x100000)？

实模式：
  mov ax, 0x????  ; 找不到合适的段值！
  mov es, ax
  mov di, 0x????
  mov [es:di], al ; 无法表达 0x100000
```

### A20 地址线的秘密

#### 什么是 A20 地址线？

**历史背景：**
```
8086 (1978):
  - 20 根地址线 (A0-A19)
  - 可以访问 1MB
  - 地址超过 1MB 时"回绕"

80286 (1982):
  - 24 根地址线 (A0-A23)
  - 可以访问 16MB
  - 但！为了兼容旧软件...
    → A20 默认被"禁用"
    → 强制回绕行为
```

**A20 线的作用：**
```
A20 禁用（默认状态）：
  物理地址的第 21 位（A20）被强制为 0
  
  示例：
    0x10FFEF → 0x00FFEF (回绕)
    0x110000 → 0x100000 (回绕)
  
A20 启用：
  正常访问所有内存
  
  示例：
    0x10FFEF → 0x10FFEF ✅
    0x110000 → 0x110000 ✅
```

#### 为什么需要启用 A20？

**不启用 A20 的后果：**
```
尝试访问 1MB (0x100000):
  → A20=0 强制
  → 实际访问 0x000000 (回绕)
  → 覆盖 BIOS 数据！
  → 系统崩溃
```

**必须启用 A20 才能：**
- ✅ 访问 1MB 以上的内存
- ✅ 加载大内核
- ✅ 使用完整的 4GB 地址空间

#### 如何启用 A20？

**方法1：BIOS 功能（推荐）**
```asm
mov ax, 0x2401      ; BIOS 功能：启用 A20
int 0x15            ; 调用 BIOS
jc .failed          ; CF=1 表示失败
```

**方法2：键盘控制器（兼容）**
```asm
; A20 线连接到键盘控制器（历史遗留）
call wait_8042
mov al, 0xD1        ; 写命令
out 0x64, al

call wait_8042
mov al, 0xDF        ; 启用 A20
out 0x60, al

wait_8042:
    in al, 0x64
    test al, 0x02
    jnz wait_8042
    ret
```

**方法3：Fast A20（现代方法）**
```asm
in al, 0x92
or al, 2
out 0x92, al
```

### Unreal 模式原理

#### 什么是 Unreal 模式？

**Unreal 模式（Big Real Mode）** = 实模式代码 + 保护模式段限制

```
普通实模式：
  代码：16 位
  段限制：64KB
  寻址：1MB

Unreal 模式：
  代码：16 位  ← 还是实模式！
  段限制：4GB  ← 保护模式的能力！
  寻址：4GB    ← 突破限制！
```

#### 为什么可以这样做？

**CPU 的秘密：段寄存器的隐藏部分**

段寄存器不只是 16 位！实际结构：

```
DS（数据段寄存器）实际结构：
┌────────────────────────────────────────┐
│ 可见部分（16位）                        │
│  - 程序可以读写                         │
│  - MOV AX, DS 读到这部分                │
├────────────────────────────────────────┤
│ 隐藏部分（描述符缓存）                   │
│  - 基址：32 位                          │
│  - 限制：32 位                          │
│  - 属性：各种标志                       │
│  - 程序不能直接访问                     │
│  - 只有 CPU 内部使用                    │
└────────────────────────────────────────┘

关键发现：
  切换到实模式时，CPU 不清空"隐藏部分"！
  → 可以保留 4GB 的段限制
  → 这就是 Unreal 模式的原理！
```

#### Unreal 模式的神奇之处

**普通实模式：**
```asm
mov ax, 0x1000
mov ds, ax

; DS 隐藏部分：
;   基址 = 0x1000 × 16 = 0x10000
;   限制 = 0xFFFF (64KB)
;
; 可访问范围：0x10000 - 0x1FFFF
```

**Unreal 模式：**
```asm
; 1. 临时进入保护模式
mov eax, cr0
or al, 1
mov cr0, eax

; 2. 加载 4GB 数据段
mov bx, 0x10        ; GDT 中的 4GB 段
mov ds, bx

; DS 隐藏部分被加载为：
;   基址 = 0x00000000
;   限制 = 0xFFFFFFFF (4GB!)  ← 关键！

; 3. 返回实模式
and al, 0xFE
mov cr0, eax

; 4. 恢复实模式段值（但隐藏部分保留！）
xor ax, ax
mov ds, ax

; 现在 DS 的状态：
;   可见部分 = 0x0000   ← 实模式
;   隐藏部分：
;     基址 = 0x00000000
;     限制 = 0xFFFFFFFF  ← 保护模式！
;
; 可访问范围：0x00000000 - 0xFFFFFFFF (4GB!)
```

**演示：使用 32 位地址**
```asm
; 现在可以用 32 位寄存器寻址！
mov edi, 0x100000      ; 1MB 地址
mov esi, 0x20000       ; 128KB 地址
mov ecx, 512           ; 复制 512 个 DWORD
a32 rep movsd          ; 使用 32 位地址！

; a32 前缀 = 地址大小覆盖
;   告诉 CPU 使用 ESI/EDI 而不是 SI/DI
```

#### Unreal 模式的优势

**对比三种模式：**

| 特性 | 实模式 | Unreal 模式 | 保护模式 |
|------|--------|------------|----------|
| 代码位数 | 16 位 | 16 位 | 32 位 |
| 可访问内存 | 1MB | 4GB | 4GB |
| BIOS 中断 | ✅ 可用 | ✅ 可用 | ❌ 不可用 |
| 实现难度 | 简单 | 中等 | 困难 |
| 性能 | 一般 | 好 | 最好 |

**为什么 Unreal 模式最适合加载内核？**

1. ✅ **保留 BIOS 功能** - 可以用 INT 13h 读磁盘
2. ✅ **访问 4GB 内存** - 可以直接写入 1MB+
3. ✅ **代码简单** - 不需要保护模式驱动
4. ✅ **Linux 标准** - GRUB 也这么做

### 直接加载到 1MB 的技巧

#### 传统方法（二次复制）

```
┌─────────────────────────────────────────┐
│ 步骤1：BIOS 读取 → 64KB 临时缓冲区      │
│        INT 13h, ES:BX = 0x1000:0x0000   │
├─────────────────────────────────────────┤
│ 步骤2：进入保护模式                     │
│        切换 CR0, 加载 GDT               │
├─────────────────────────────────────────┤
│ 步骤3：复制到 1MB                       │
│        memcpy(0x100000, 0x10000, size)  │
└─────────────────────────────────────────┘

问题：
  - 两次内存操作
  - 需要临时缓冲区
  - 内核大小受限于缓冲区
```

#### Unreal 模式方法（直接加载）

```
┌─────────────────────────────────────────┐
│ 步骤1：进入 Unreal 模式                 │
│        临时保护模式 → 加载 4GB 段       │
│        → 返回实模式（保留段限制）       │
├─────────────────────────────────────────┤
│ 步骤2：BIOS 读取 → 临时缓冲区（128KB）  │
│        INT 13h, ES:BX = 0x2000:0x0000   │
├─────────────────────────────────────────┤
│ 步骤3：32位复制 → 1MB 目标地址          │
│        mov edi, 0x100000                │
│        mov esi, 0x20000                 │
│        a32 rep movsd      ← 直接写入！  │
├─────────────────────────────────────────┤
│ 重复步骤2-3，直到整个内核加载完毕       │
└─────────────────────────────────────────┘

优势：
  ✅ 一次到位，无需二次复制
  ✅ 支持任意大小内核
  ✅ BIOS 功能仍可用
```

#### 为什么要用临时缓冲区？

**BIOS INT 13h 的限制：**
```
INT 13h 参数：
  ES:BX = 目标地址

问题：
  ES = 段寄存器（16 位）
  BX = 偏移（16 位）
  
  ES:BX 最大 = 0xFFFF:0xFFFF ≈ 1MB
  
不能直接指定 1MB+ 的地址！
  → BIOS 函数不认识 32 位地址
```

**解决方案：**
```
1. BIOS 读到低端内存（比如 128KB 处）
   INT 13h, ES:BX = 0x2000:0x0000  ✅ BIOS 能理解

2. 使用 Unreal 模式的 32 位复制
   movsd [edi], [esi]  ; EDI=1MB, ESI=128KB ✅ CPU 能执行

3. 循环加载所有扇区
```

## 第三部分：实现细节

### 代码实现：进入 Unreal 模式

#### 完整代码（带详细注释）

```asm
; ===========================================================================
; enter_unreal_mode - 进入 Unreal 模式
; ===========================================================================
; 功能：在实模式代码中获得 4GB 寻址能力
; 前提：A20 必须已启用，GDT 已加载
; 返回：DS, ES 具有 4GB 限制，但仍在实模式
; ===========================================================================

enter_unreal_mode:
    push eax
    push ds
    
    ; --- 第1步：关闭中断 ---
    ; 原因：切换模式时不能被中断
    cli
    
    ; --- 第2步：加载 GDT ---
    ; GDT 中必须有一个 4GB 的数据段
    lgdt [gdt_descriptor]
    
    ; --- 第3步：进入保护模式 ---
    mov eax, cr0
    or al, 1                    ; 设置 PE 位（Protection Enable）
    mov cr0, eax
    ; 现在 CPU 处于保护模式
    
    ; --- 第4步：加载 4GB 数据段到 DS/ES ---
    mov bx, 0x10                ; GDT 第2项（4GB 数据段）
    mov ds, bx
    mov es, bx
    
    ; 关键时刻：
    ;   CPU 从 GDT 读取段描述符
    ;   将 4GB 限制加载到 DS/ES 的"隐藏部分"
    ;
    ;   DS 隐藏部分现在包含：
    ;     Base  = 0x00000000
    ;     Limit = 0xFFFFFFFF
    ;     Flags = Granularity=1, Size=1
    
    ; --- 第5步：返回实模式 ---
    and al, 0xFE                ; 清除 PE 位
    mov cr0, eax
    ; 现在 CPU 回到实模式
    
    ; --- 第6步：恢复实模式段值 ---
    ; 重要：只改变可见部分，隐藏部分不变！
    xor ax, ax
    mov ds, ax
    mov es, ax
    
    ; 最终状态：
    ;   DS/ES 可见部分 = 0x0000  (实模式)
    ;   DS/ES 隐藏部分 = 4GB限制 (保护模式)
    ;
    ; 结果：可以用 32 位地址访问 4GB 内存！
    
    ; --- 第7步：重新启用中断 ---
    sti
    
    pop ds
    pop eax
    ret
```

#### GDT 设置（关键）

```asm
; Unreal 模式需要的 GDT
align 8
gdt_start:

; NULL 描述符（GDT 第0项，必须为空）
gdt_null:
    dd 0x00000000
    dd 0x00000000

; 代码段描述符（GDT 第1项，选择子 0x08）
; 这个用于保护模式，Unreal 模式不用
gdt_code:
    dw 0xFFFF          ; 段限制 (低16位) = 0xFFFF
    dw 0x0000          ; 段基址 (低16位) = 0x0000
    db 0x00            ; 段基址 (中8位)  = 0x00
    db 10011010b       ; 访问字节：P=1, DPL=0, S=1, Type=1010(代码,可读可执行)
    db 11001111b       ; 标志+限制：G=1, D=1, L=0, AVL=0, 限制(高4位)=F
    db 0x00            ; 段基址 (高8位)  = 0x00
    
; 完整的段限制 = 0xFFFFF
; G=1（粒度=4KB）→ 实际限制 = 0xFFFFF * 4KB = 4GB

; 数据段描述符（GDT 第2项，选择子 0x10）← Unreal 模式用这个！
gdt_data:
    dw 0xFFFF          ; 段限制 (低16位)
    dw 0x0000          ; 段基址 (低16位)
    db 0x00            ; 段基址 (中8位)
    db 10010010b       ; 访问字节：P=1, DPL=0, S=1, Type=0010(数据,可读可写)
    db 11001111b       ; G=1, D=1 → 4GB 数据段
    db 0x00            ; 段基址 (高8位)

gdt_end:

gdt_descriptor:
    dw gdt_end - gdt_start - 1    ; GDT 大小-1
    dd gdt_start                  ; GDT 地址

; 关键参数解释：
; G (Granularity) = 1
;   → 段限制单位是 4KB 而不是字节
;   → 0xFFFFF × 4KB = 4GB
;
; D (Default size) = 1  
;   → 32 位段
;   → 支持 32 位操作数和地址
```

#### 逐步分析

**步骤1-2：为什么要 CLI 和加载 GDT？**
```
CLI（关闭中断）：
  切换模式时 CPU 状态不稳定
  中断可能导致崩溃
  
LGDT（加载 GDT）：
  保护模式需要 GDT
  Unreal 模式需要从 GDT 加载 4GB 段描述符
```

**步骤3-4：为什么要临时进入保护模式？**
```
在实模式下：
  MOV DS, AX  → 只设置段值，不读 GDT
  
在保护模式下：
  MOV DS, BX  → BX 是选择子，CPU 从 GDT 读取描述符
               → 加载到段寄存器的"隐藏部分"
               
这是我们想要的！
```

**步骤5-6：为什么返回实模式还能保留 4GB 限制？**
```
CPU 设计特性：
  进入实模式时，只清除 CR0.PE 位
  不清空段寄存器的隐藏部分！
  
  这是 Intel 的"未文档化特性"
  → 但是标准行为，所有 x86 CPU 都这样
  → GRUB 和 Linux 依赖这个特性
```

### 代码实现：大内核加载循环

#### 完整的加载循环

```asm
; ===========================================================================
; load_kernel_big - 加载大内核到 1MB
; ===========================================================================
; 功能：使用 Unreal 模式直接加载大内核到 1MB 物理地址
; 前提：已进入 Unreal 模式，A20 已启用
; 参数：无（从全局变量读取）
; 返回：CF=0 成功，CF=1 失败
; ===========================================================================

KERNEL_START_SECTOR equ 9       ; 内核从第 9 扇区开始
KERNEL_LOAD_ADDR equ 0x100000   ; 加载到 1MB
TEMP_BUFFER equ 0x20000         ; 临时缓冲区（128KB 处）

load_kernel_big:
    push eax
    push ebx
    push ecx
    push edx
    push esi
    push edi
    
    ; --- 初始化 ---
    mov edi, KERNEL_LOAD_ADDR    ; EDI = 目标地址（1MB）
    mov ecx, 0                   ; ECX = 已加载扇区数
    mov dx, [kernel_size_sectors]; DX = 总扇区数（默认 4096 = 2MB）
    
.load_loop:
    ; --- 检查是否完成 ---
    cmp cx, dx
    jae .success                ; 已加载全部扇区
    
    ; --- 计算本次加载扇区数 ---
    ; 每次最多 127 扇区（BIOS 限制）
    mov ax, dx
    sub ax, cx                  ; AX = 剩余扇区数
    cmp ax, 127
    jbe .do_read
    mov ax, 127                 ; 限制为 127
    
.do_read:
    ; --- 设置 DAP（磁盘地址包）---
    mov word [dap_sectors], ax
    mov word [dap_offset], 0
    mov word [dap_segment], 0x2000  ; 临时缓冲区段（128KB）
    
    ; 计算 LBA（逻辑块地址）
    mov ax, cx
    add ax, KERNEL_START_SECTOR
    movzx eax, ax
    mov dword [dap_lba_low], eax
    mov dword [dap_lba_high], 0
    
    ; --- 调用 BIOS 读取扇区 ---
    mov ah, 0x42                ; INT 13h 扩展读取
    mov dl, [boot_drive]        ; 驱动器号
    mov si, dap                 ; DS:SI = DAP
    int 0x13
    jc .error                   ; CF=1 表示错误
    
    ; --- 使用 Unreal 模式复制到 1MB ---
    ; 保存当前状态
    push cx
    push edi
    
    ; 源地址：0x20000（临时缓冲区）
    ; 目标地址：EDI（1MB+）
    mov esi, TEMP_BUFFER
    movzx ecx, word [dap_sectors]  ; ECX = 扇区数
    shl ecx, 7                     ; × 128 (512 字节/扇区 ÷ 4 字节/DWORD)
    
    ; 32 位内存复制（Unreal 模式的魔力！）
    a32 rep movsd
    ; a32 = 地址大小前缀
    ;   → 使用 ESI/EDI（32位）而不是 SI/DI（16位）
    ;   → 可以访问 4GB 内存
    
    ; 恢复状态
    pop edi
    pop cx
    
    ; --- 更新指针 ---
    movzx eax, word [dap_sectors]
    shl eax, 9                  ; × 512 字节
    add edi, eax                ; 更新目标地址
    add cx, word [dap_sectors]  ; 更新已加载扇区数
    
    jmp .load_loop
    
.success:
    clc                         ; CF=0 表示成功
    jmp .done
    
.error:
    stc                         ; CF=1 表示失败
    
.done:
    pop edi
    pop esi
    pop edx
    pop ecx
    pop ebx
    pop eax
    ret

; DAP（磁盘地址包）结构
dap:
    db 0x10                     ; DAP 大小
    db 0                        ; 保留
dap_sectors:
    dw 0                        ; 要读取的扇区数
dap_offset:
    dw 0                        ; 目标偏移
dap_segment:
    dw 0                        ; 目标段
dap_lba_low:
    dd 0                        ; LBA 低 32 位
dap_lba_high:
    dd 0                        ; LBA 高 32 位

kernel_size_sectors:
    dw 4096                     ; 默认 2MB
```

#### 关键代码逐行解析

**`a32 rep movsd` - 最核心的指令**

```asm
a32 rep movsd

分解：
  a32      = 地址大小覆盖前缀
  rep      = 重复前缀（重复 ECX 次）
  movsd    = 移动双字（4字节）
  
执行过程：
  while (ECX > 0) {
      [EDI] = [ESI];      // 复制 4 字节
      ESI += 4;           // 源地址 +4
      EDI += 4;           // 目标地址 +4
      ECX--;
  }
  
为什么需要 a32？
  在 16 位代码模式下（实模式）：
    默认使用 SI/DI（16位）
    a32 强制使用 ESI/EDI（32位）
    
  这样才能访问 1MB 以上的地址！
```

**为什么用 `movzx`？**

```asm
movzx ecx, word [dap_sectors]

movzx = Move with Zero-Extend（零扩展移动）

作用：
  将 16 位值复制到 32 位寄存器，高位填0
  
  示例：
    [dap_sectors] = 127 (16位)
    movzx ecx, word [dap_sectors]
    ECX = 0x0000007F (32位)
    
为什么需要？
  rep movsd 需要 ECX 是 32 位
  如果用 mov cx, [dap_sectors] 只设置低16位
  高 16 位可能是脏数据！
```

**为什么 `shl ecx, 7`？**

```asm
shl ecx, 7      ; ECX 左移 7 位 = × 128

计算：
  1 扇区 = 512 字节
  1 DWORD = 4 字节
  
  扇区数 → DWORD数：
    = 扇区数 × 512 ÷ 4
    = 扇区数 × 128
    = 扇区数 << 7
```

### 代码实现：错误处理

#### 为什么需要错误处理？

**可能的失败场景：**
1. BIOS 不支持 INT 13h 扩展
2. 磁盘读取失败（坏道、硬件故障）
3. 内核镜像损坏
4. 磁盘参数错误

#### 检测 INT 13h 扩展支持

```asm
; 在加载前检测
detect_int13h_ext:
    mov ah, 0x41            ; 检测扩展功能
    mov bx, 0x55AA          ; 魔数
    mov dl, [boot_drive]
    int 0x13
    jc .not_supported       ; CF=1 不支持
    
    cmp bx, 0xAA55          ; 检查返回魔数
    jne .not_supported
    
    ; 支持！
    ret
    
.not_supported:
    ; 显示错误并停机
    mov si, msg_no_int13h
    call print_string
    jmp hang
    
msg_no_int13h:
    db 'ERROR: BIOS does not support INT 13h Extensions', 0x0D, 0x0A
    db 'Cannot load large kernel.', 0x0D, 0x0A, 0
```

#### 重试机制

```asm
; 读取失败时重试（最多3次）
.do_read:
    mov byte [retry_count], 3
    
.retry:
    ; 执行读取
    mov ah, 0x42
    mov dl, [boot_drive]
    mov si, dap
    int 0x13
    jnc .read_ok            ; 成功！
    
    ; 失败，重试
    dec byte [retry_count]
    jnz .retry
    
    ; 3次都失败，报错
    jmp .error
    
.read_ok:
    ; 继续...
    
retry_count:
    db 0
```
